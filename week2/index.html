루프 안의 판단은 대부분 닫힌 선택이다

  • 이 요청을 어느 모델로 보낼까 (라우팅)
  • 이 명령은 위험한가 (가드)
  • 이 로그는 어떤 종류인가 (분류)
  • 작업이 끝났는가 (완료 판정)

그런데도 매번 생성 모델을 부른다

  • 판단 한 번이 모델 호출 한 번이다
  • LangChain은 이 구조가 루프를 느리고 비싸게 만든다고 지적했다
  • 판단의 형식은 선택인데 수단은 글쓰기다
문제

선택지 중 하나를 고르는 판단에도 글을 생성하는 모델을 쓰면, 에이전트 루프의 시간과 비용이 판단 횟수만큼 쌓인다.

실습판단 단계를 결정 모델로 바꾸면 무엇이 줄어드는가슬라이더로 조건을 바꿔 보기

01 배경System 1과 System 2

TypeSafe는 빠른 판단을 System 1로, 숙고와 생성을 System 2로 나눴다

System 1 · 빠르고 직관적인 판단

  • 한눈에 스팸을 알아보는 종류의 판단
  • 정해진 선택지 중 하나를 고르고 확률을 붙인다
  • TypeSafe가 Jev를 'System One 모델'로 부른 이유

System 2 · 느리고 숙고하는 처리

  • 긴 추론, 계획, 코드와 글의 생성
  • 선택지가 정해지지 않은 열린 문제
  • 예외가 생겼을 때만 부르는 상위 단계
이름은 카너먼의 『Thinking, Fast and Slow』(2011)에서 빌렸다. 범주가 퍼지면서 업계 용어는 'System One 모델'보다 결정 모델(decision model)로 굳었다 (Waehner, 2026. 10. 20).
주의

System 1·2는 카너먼의 비유를 빌린 이름이다. 모델이 사람의 인지 구조를 따른다는 뜻은 아니다.

01 배경이 강의에서 쓰는 용어

결정 모델을 설명하는 여덟 가지 용어

용어이 강의에서의 뜻
결정 모델상태와 타입이 정해진 질문을 받아, 글 대신 확률이 붙은 답을 돌려주는 모델. Jev가 첫 공개 사례다
상태 (state)판단의 근거가 되는 입력. 텍스트나 JSON이며 Jev는 질문 하나와 합쳐 32k, 요청 전체 64k 토큰까지 받는다
질문 타입Choice(선택), Score(순서 척도), Noul(참일 확률). 1.14에서 이미지용 Box(경계 상자)가 더해졌다
확신도모델이 자기 답에 붙이는 확신의 크기. 코드가 자동 실행 여부를 가르는 기준이 된다
보정 (calibration)말한 확신도와 실제로 맞는 비율이 일치하는 정도. 90%라고 말한 답이 실제로 90% 맞으면 잘 보정된 것이다
루브릭선택지마다 무엇에 해당하고 무엇에 해당하지 않는지를 적은 정의 묶음. 프롬프트 대신 쓰는 판단 기준
하네스모델을 둘러싼 실행 환경. 권한, 재시도, 검증, 사람 승인, 기억 저장 규칙 같은 통제 장치 전체
Jev 엔지니어링LLM은 쓰고, 결정 모델은 판단하고, 코드는 행동하도록 역할을 나누는 설계 방식
핵심 구분

확신도는 모델이 말하는 값이고, 보정은 그 값을 믿어도 되는지에 대한 측정이다. 이 둘을 섞으면 뒤의 '한계와 검증'에서 다룰 문제를 놓친다.

Waehner는 결정 모델을 과제마다 학습하는 고전 ML과 생성형 LLM 사이에 두고, 둘을 대체하기보다 보완한다고 정리했다.

02 Jev그림 2 · Jev의 입력과 출력

Jev는 상태와 질문을 받아 확률이 붙은 답을 한 번에 돌려준다

상태 (state)텍스트·JSON
→
질문 목록Choice · Score · Noul
→
Jev한 번의 처리 · 병렬 평가
→
타입이 정해진 답선택 + 확률 + 확신도
→
코드임계값 확인 후 행동

하는 일

  • 모든 질문을 한 번에 병렬로 평가한다
  • 답을 토큰 단위로 하나씩 이어 쓰지 않는다
  • 답은 항상 주어진 선택지 안에서 나온다

하지 않는 일

  • 글이나 코드를 쓰지 않는다. 회사는 문자열 생성을 포기했다고 밝혔다
  • 판단 이유를 문장으로 돌려주지 않는다
  • 목록에 없는 선택지는 고르지 않는다
핵심

출력이 확률 값이므로 코드는 파싱 없이 바로 분기 조건으로 쓸 수 있다.

02 Jev질문의 세 가지 타입

질문은 Choice, Score, Noul 세 가지 타입으로 정의한다

타입묻는 것돌려주는 것쓰임 예
Choice이 선택지들 중 무엇인가 (1~255개)선택, 모든 선택지의 확률, 확신도요청 종류 분류, 모델 등급 고르기
Score1~10단계 척도에서 어디인가확률 가중 기댓값, 단계별 확률, 확신도로그 심각도, 위험도 등급
Noul이 문장이 참인가참일 확률 하나. 확신도 필드 없음이 명령은 파괴적인가
 
state: "사용자가 실행하려는 명령: rm -rf ./dist"
questions:
  - noul:   "이 명령은 되돌릴 수 없는 삭제를 일으킨다"
  - choice: "명령의 종류" [삭제, 읽기, 설치, 네트워크, unknown]
  - score:  "위험도" [낮음, 중간, 높음]

질문 구성 예시 (구조 설명용 의사 형식). 실제 요청 형식은 TypeSafe API 문서를 따른다. 1.14에는 이미지 속 경계 상자를 묻는 Box 타입이 더해졌다.

에이전트 루프를 상태, 판단, 행동, 검증, 다음 상태의 제어 시스템으로 본다

상태입력·기록
→

→

→

→

↺ 다시 처음으로

확신도가 높을 때

  • 코드가 미리 정한 행동을 바로 실행한다
  • LLM을 부르지 않는다
  • 비용과 지연이 결정 모델 호출 한 번에 머문다

확신도가 낮거나 unknown일 때

  • 상위 모델이나 사람에게 넘긴다
  • LLM이 원인을 보고 루브릭 수정안을 쓴다
  • 수정안은 검증을 거쳐 다음 판단부터 쓰인다
효과

판단이 확률로 나오기 때문에 '언제 큰 모델을 부를지'가 코드 한 줄의 임계값 문제로 바뀐다.

03 Jev 엔지니어링기법 1 · Guard Hook

가드 훅은 명령을 실행하기 전에 파괴적인지 묻고 확률 구간으로 막는다

입력 명령과 판정 (글쓴이 시연)

DROP TABLE users;파괴적 0.95차단
rm -rf ./dist파괴적 0.63사용자에게 묻기
ls -la낮음 (예시)허용

핵심 아이디어

에이전트가 도구를 쓰기 직전(PreToolUse 훅)에 Noul 질문 '이 명령은 파괴적인가'와 Choice 질문 '명령의 종류'를 함께 보낸다. 0.7 이상이면 차단, 0.35 이상이면 사용자에게 묻는다. Jev 호출이 실패하면 허용하지 않고 사용자에게 묻는다.

원본 출처: AI Builder Club, 2026. 09. 22 · LangChain AutoModeMiddleware도 같은 목적 (2026. 09. 17). 호출이 실패했을 때의 기본값은 '묻기'로 둔다. 임계값은 행동의 되돌리기 어려움에 맞춰 정한다.

주의

시연은 명령 여섯 개 규모라 평가가 아니다. 'ls -la'의 값은 설명을 위한 예시다. 분류기 하나에 맡기면 단일 실패 지점이 되므로 권한 설정은 그대로 둔다.

실습임계값 두 개로 허용·묻기·차단 가르기임계값을 움직여 놓친 위험과 불필요한 묻기를 보기
놓친 위험0
불필요한 묻기·차단0
자동 처리0
'정답'은 사람이 붙인 라벨(위험 = 되돌릴 수 없는 변경)이다. DROP 0.95와 rm 0.63은 글쓴이 시연값, 나머지 명령과 확률은 예시다. 실습에서는 명령 30개를 모아 위험한 명령을 하나도 놓치지 않는 임계값부터 찾는다.
03 Jev 엔지니어링기법 2 · Model Router

모델 라우터는 요청마다 모델 등급을 고르고, 확신이 낮으면 한 단계 위로만 올린다

라우팅 흐름

사용자 요청Choice: fast / powerful확신도 확인
확신도 높음고른 등급 그대로실행
확신도 낮음한 단계 위 등급으로실행 (아래로는 내리지 않음)

핵심 아이디어

요청을 받으면 Choice 질문으로 모델 등급을 고른다. 확신도가 낮으면 한 단계 위 모델로만 올리고, 아래로는 내리지 않는다. 비용을 아끼되 품질 손해는 피하는 비대칭 규칙이다.

원본 출처: AI Builder Club, 2026. 09. 22 · LangChain ModelRouterMiddleware (최신 사용자 메시지로 판단하고 실행이 끝날 때까지 유지). 글쓴이 측정: 전형적 호출 약 500 입력 토큰, 약 $0.00002, 280~610ms. 등급 정의는 루브릭으로 관리한다.

설계 원칙

불확실할 때는 비싼 쪽으로 기운다. 잘못 싼 모델로 보낸 손해가 잘못 비싼 모델로 보낸 비용보다 크기 때문이다.

로그 분류 크론은 처음 보는 유형만 LLM에 넘겨 루브릭을 키운다

03 Jev 엔지니어링기법 4 · 프롬프트 대신 루브릭

판단 기준을 프롬프트 문장에서 꺼내 버전을 관리하는 루브릭 데이터로 옮긴다

{
  "id": "destructive_delete",
  "what": "파일·DB를 되돌릴 수 없게 지우는 명령",
  "not_for": "빌드 산출물만 지우는 정리 명령 (별도 항목)",
  "examples": ["DROP TABLE users;", "rm -rf ~/projects"]
}
선택지 목록: [destructive_delete, cleanup, read,
             install, network, unknown]

루브릭 한 항목의 구조 (예시). AI Builder Club이 권장한 what · not_for · examples 구조를 따라 새로 쓴 예시다.

규칙

  • 선택지는 닫힌 집합으로 정하고 unknown을 꼭 넣는다
  • 항목마다 해당하지 않는 경우(not_for)를 적는다
  • 루브릭은 코드처럼 버전을 붙여 관리한다

이유

  • 결정 모델은 목록에 없는 답을 못 고르므로 unknown이 탈출구가 된다
  • 경계 사례가 not_for에 쌓이면서 기준이 정밀해진다
  • 어느 버전의 기준으로 판단했는지 추적할 수 있다
1주차와 연결

1주차의 '독려 문구에서 범위 정하기로'라는 변화가 여기서는 '문장 대신 정의된 선택지'라는 형태로 한 단계 더 나아간다.

03 Jev 엔지니어링기법 5 · 확신도에 따른 분기

확신도가 낮은 답은 자동으로 적용하지 않고 위로 넘긴다

실제 사례에 라벨실제로 들어오는 입력 20~50개에 정답 라벨을 붙인다
행동마다 하한 설정되돌리기 어려운 행동일수록 확신도 하한을 높게 둔다
하한 미만은 위로상위 모델이나 사람에게 넘기고, 넘긴 비율을 기록한다
자동 적용 금지확신도가 낮은 답은 어떤 경우에도 자동으로 실행하지 않는다
모델 버전 고정jev-latest 같은 별칭은 기준이 몰래 바뀌게 만든다
근거

라벨 20~50개, 버전 고정은 AI Builder Club의 권고다. 실제로 jev-latest는 10월 하순 1.14.0으로 바뀌었다. 라벨이 몇 개면 충분한지는 과제마다 직접 측정한다.

"Jev does not replace permissions, deterministic checks, or human approval." 결정 모델의 확률은 더 큰 통제 시스템 안의 신호 하나다 (Daily Dose of DS, 2026. 10. 01).

03 Jev 엔지니어링실습 · 가드 훅 만들기

실습: 결정 모델로 위험 명령 가드 훅을 만든다

def pre_tool_use(command):
    try:
        r = decide(state=command, questions=[
            noul("이 명령은 되돌릴 수 없는 변경을 일으킨다"),
            choice("종류", RUBRIC_V3)])      # 루브릭 버전 고정
    except Timeout:
        return ASK_USER                      # 실패하면 허용하지 않는다
    p = r[0].prob
    if p >= 0.70: return DENY
    if p >= 0.35 or r[1].choice == "unknown": return ASK_USER
    return ALLOW

의사 코드 (특정 SDK의 실제 함수명이 아니다). 임계값 0.70 / 0.35는 AI Builder Club 시연값이다. 실습에서는 각자 라벨링한 명령으로 다시 정한다.

명령 30개 모으기평소 에이전트가 실행하는 명령을 위험한 것과 안전한 것을 섞어 모은다
라벨 붙이기사람이 '되돌릴 수 없는 변경인가'를 직접 판정한다
임계값 맞추기위험한 명령을 하나도 놓치지 않는 값부터 찾는다
실습 규칙

실습은 격리된 디렉터리에서 한다. 판정 결과와 상관없이 실제 삭제 명령은 실행하지 않는다.

  • 보정 오차를 따로 재는 제3자 시험
주의

회사마다 자기 인터페이스에 맞는 부분집합으로 벤치마크를 돌려 수치가 엇갈린다 (Waehner). 같은 이름의 점수라도 같은 잣대인지 먼저 본다.

04 결정 모델 계열갈래의 분화

결정 모델은 멀티모달, 짧은 추론, 보안 전용, 미세조정 갈래로 나뉘고 있다

멀티모달

  • OpenAI Decisions API: 텍스트·이미지·JSON
  • Cloudflare Clef-omni: 오디오·영상·이미지·텍스트
  • Jev: 이미지는 실험 기능, 1.14에 경계 상자(Box) 질문

짧은 추론

  • 기존 LLM을 결정 인터페이스 뒤에 두는 방식
  • 답하기 전에 잠깐 추론하는 방식
  • 둘 다 지연을 늘리는 대신 어려운 사례의 정확도를 높인다

보안 전용

  • Superagent Security-One (10. 04, 27B, Apache 2.0)
  • 프롬프트, 도구 호출, 코드 변경, 경보에 대한 보안 판단

미세조정

  • 결정 모델을 바탕으로 자체 라벨로 미세조정
  • 강화학습 미세조정 플랫폼이 지원
흐름

출시 때 실험 기능이던 이미지 입력이 한 달 사이 다른 회사들의 정식 입력이 되었다. 출시 때 적힌 한계가 지금도 맞는지 매번 다시 확인해야 하는 이유다.

04 결정 모델 계열원조 논쟁

원조 논쟁은 아이디어를 먼저 낸 것과 범용 제품으로 만든 것의 차이를 보여 준다

주장

  • ConvAI Innovations 창업자 Nandakishor Mukkunnoth
  • '1년 전에 Jev 구조를 설계했다'는 주장 (Tom's Hardware 인용)
  • 근거: SalesRLAgent (arXiv 2503.23303, 2025. 03), 신뢰도 기반 라우팅 논문 (arXiv 2510.01237, 2025. 09)

차이

  • 그의 연구는 판매라는 특정 업종의 확률 추정과 라우팅
  • Jev는 범용 결정 엔진에 API, 문서, 가격을 갖춘 제품
  • 그는 오픈소스 Laya를 함께 공개했다

현재

  • 논쟁은 09. 20 무렵부터 보도되었다
  • Tom's Hardware(10. 12)까지 TypeSafe의 응답은 보도되지 않음
  • 기사도 누가 먼저인지 판단하지 않음
토론 거리

연구 아이디어의 기여와 제품화의 기여를 각각 어떻게 인정할지. 이 강의는 어느 쪽이 옳다고 판단하지 않는다.

05 한계와 검증한국어

한국어 입력에서는 성능을 따로 재야 한다

회사가 밝힌 것

  • 영어에서 가장 정확하다
  • 한중일 언어를 포함한 다른 언어는 처리하지만 같은 수준은 아니다
  • 1.14의 개선은 다국어에 집중된다고 밝혔다

그래서 할 일

  • 실제 한국어 입력 20~50개에 라벨
  • 한국어용 확신도 하한을 따로 정함
  • 상위 모델로 넘기는 비율을 언어별로 기록

참고할 데이터

  • MASSIVE: 51개 언어, 약 100만 발화의 의도·슬롯 데이터 (arXiv 2204.08582)
  • 한국어 부분으로 의도 분류를 먼저 확인
대안

Laya처럼 다국어 인코더(mmBERT)를 쓴 오픈 모델도 있다. 언어 성능이 핵심인 과제에서는 후보를 같은 한국어 라벨 세트로 비교한다.

05 한계와 검증보안

판단을 분류기 하나에 맡기면 그 분류기가 단일 실패 지점이 된다

위험

  • 적대적 입력은 분류기를 속이도록 만들어진다
  • 루브릭 예시와 다른 입력에서는 보정이 나빠질 수 있다
  • 라벨 뒤집힘 민감도와 적대적 강건성이 평가 과제로 지적됨

대응

  • 적대적 입력에는 2차 검사를 둔다
  • 권한·샌드박스·사람 승인은 그대로 유지한다
  • 실패하거나 애매하면 차단·묻기 쪽으로 기본값을 둔다
1주차 연결: 적응형 공격은 최근 방어 12개 대부분에서 90%를 넘는 성공률을 얻었다(The Attacker Moves Second, arXiv 2510.09023). 결정 모델 기반 가드도 같은 시험 대상이다.
원칙

결정 모델은 방어의 여러 층 가운데 하나다. 1주차 결론처럼 억제는 권한·격리·정보 흐름 설계에 남겨 둔다.

05 한계와 검증쓰지 말아야 할 때

결정 모델을 쓰지 말아야 하는 경우가 분명히 있다

경우이유대신 쓸 것

정리

반복되고, 선택지가 닫혀 있고, 틀렸을 때 위로 넘길 길이 있는 판단에 결정 모델을 쓴다.

강의자 판단

결정 모델처럼 새 범주를 연 것은 아직 보이지 않는다. 대부분 기존 흐름을 한 단계 밀어낸 것에 가깝고, 공개 범위도 프리뷰에 머문다.

결론2주차 정리

판단을 생성에서 떼어 내면 에이전트 설계의 단위가 바뀐다

1

분업

LLM은 쓰고, 결정 모델은 판단하고, 코드는 행동한다. 큰 모델은 처음 보는 경우를 풀어 기준을 넓히는 데만 쓴다.

2

확률은 신호

확신도는 순위로 쓰고 값은 믿지 않는다. 임계값은 자기 데이터, 특히 한국어 라벨로 다시 맞춘다.

3

하네스가 먼저

결정 모델은 권한, 결정적 검사, 사람 승인을 대체하지 않는다. 1주차 결론대로 억제는 시스템 설계에 둔다.
