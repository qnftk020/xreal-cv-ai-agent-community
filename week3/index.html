요약이 강의의 줄기

에이전트가 빨라질수록 고민은 "어떻게 만들까"에서 "언제 믿을까"로 옮겨 갔다

2월에는 GitHub 웹에 파일을 끌어다 올렸다. 10월에는 클라우드 에이전트가 하루에 커밋을 백 개 넘게 쌓았고, 사람은 검토와 거부권을 쥐는 쪽으로 옮겨 갔다. 그 사이 10개월 동안 바뀐 것은 코드를 쓰는 손이 아니라 에이전트가 만든 결과를 믿기 전에 무엇을 확인하느냐였다.

믿을까?

에이전트의 결과를 언제 믿나

지어낸 수치, 다른 논문, 검토 안 된 병합. 그럼 검증은 운영 앞에 있어야 하지 않을까?

어디에?

사람은 어디에 서 있어야 하나

매번 누르는 승인이 필요할까, 이상할 때만 쓰는 거부권이면 되지 않을까?

조용히?

조용히 실패하는 걸 어떻게 아나

오류도 없이 멈춘 게 제일 위험한 것 아닐까?

2주차와 연결

2주차는 판단을 맡는 모델과 그 둘레의 하네스(권한, 검증, 사람의 승인)를 다뤘다. 3주차는 한 사람이 10개월 동안 그 하네스를 고민하며 하나씩 만들어 간 기록이다.

01 고민의 순서10개월, 다섯 시기

도구가 바뀔 때마다 고민이 한 단계씩 옮겨 갔다

시기도구그때의 고민내린 결정
2월 ~ 3월 초없음 (웹 업로드·손 편집)일단 올라가게 할 수 있나결과 파일을 옮겨 놓는 수준에서 시작
3월 ~ 5월Claude Opus 4.6 → 4.8무엇을 만들고 싶은가만들어 보고 마음에 안 들면 갈아엎기. 검증은 눈으로
6월 ~ 8월Claude Fable 5, Opus 4.8, Cursor그 결과가 정말 맞나사고가 날 때마다 검증 단계와 규칙을 적기 시작
9월Codex, Claude Opus 5.5사람의 주의를 어디에 쓸까첫 테스트·CI, "정상이면 조용히, 이상만 알린다"
10월 ~ 11월Claude Opus 5.5 (로컬 + 클라우드 세션)에이전트가 나보다 빠를 때 무엇을 지키나독립 검토, 거부권, 맥 없이 도는 운영
읽는 법

오른쪽 두 칸이 이 강의의 본론이다. 다음 장부터 고민 일곱 가지를 하나씩 본다.

02 고민고민 1 · 검증

에이전트의 결과는 언제 믿어도 되는가

무슨 일이 있었나
  • VR 논문 기록에 번역 AI 논문의 DOI·PDF·리뷰가 섞여 들어갔다 (7/4~5)
  • 제목만 보고 쓴 리뷰에 LLM이 지어낸 수치가 들어갔다
  • 근거 없는 로봇 가격과 엉뚱한 연구가 큐레이션에 들어왔다
  • 검토하지 않은 클라우드 커밋 약 40개가 섞인 채 병합됐다 (10/18)
무엇을 고민했나

에이전트는 그럴듯하게 틀리지 않나? 결과를 보기 전에 그 논문이 맞는지, 그 숫자가 원문에 있는지부터 물어야 하지 않을까? 에이전트가 이렇게 빨라지는데, 사람 혼자 눈으로 보는 검토가 과연 따라갈 수 있을까?

무엇으로 정했나
  • 논문 정체성 검증, 제목만으로 쓰는 리뷰 금지
  • 리뷰 속 숫자를 원문과 대조하는 자동 검사
  • 병합·배포 전에 독립 검토 에이전트 6개가 따로 본다
원칙

에이전트의 결과는 검증된 뒤에만 운영에 들어간다. 에이전트가 빨라질수록 검토는 더 독립적이어야 한다.

02 고민고민 2 · 사람의 자리

사람은 매번 승인해야 하는가, 아니면 거부권만 쥐면 되는가

무슨 일이 있었나
  • 승인 링크를 눌러야 메일이 나가는 구조는 사람이 바쁜 날 그냥 멈췄다
  • 수동 승인 → 자동 승인 → 롤백 → 재도입을 오갔다
  • 매일 오는 전체 미리보기 메일은 점점 읽히지 않았다
무엇을 고민했나

승인 단계가 실제로 무엇을 막고 있었나? 세어 보니 승인 클릭을 놓쳐 못 나간 날이 3번, 사람이 승인에서 걸러 낸 경우는 0번이었다. 그렇다면 내 클릭은 안전장치가 아니라 병목이 아니었을까?

무엇으로 정했나
  • 기본은 자동 승인
  • 22:00 미리보기의 "발송 취소"와 보류만 사람 몫
  • 리뷰가 모두 정상이면 메일이 오지 않는다 (9/22)
원칙

사람의 승인은 줄이되 거부권은 남긴다. 사람의 주의는 예외에만 쓴다.

02 고민고민 3 · 조용한 실패

오류 없이 멈춘 것은 어떻게 알아차리는가

무슨 일이 있었나
  • 메일 API가 오류를 던지지 않고 돌려주는데 호출부 6곳이 모두 무시했다 (7/25)
  • 베뉴 경보가 엉뚱한 출력만 보고 있어 2주 동안 한 건도 못 잡았다
  • 보안 위젯은 두 달간 직접 구독이 0건이었고, 뉴스 수집은 한 번도 돌지 않았다
무엇을 고민했나

이것들을 사용자가 알려 줬나? 아니, 전부 점검하다가 찾았다. 요란하게 터지는 오류보다 아무 말 없이 멈춘 게 더 위험한 것 아닐까? 60일 동안 커밋이 없으면 조용히 꺼지는 GitHub 예약 작업도 결국 같은 이야기 아닐까?

무엇으로 정했나
  • "실패하면 반드시 메일 한 통"을 기본값으로
  • 꺼질 수 있는 예약 작업은 미리 Cloudflare Worker로
  • 정상일 때 조용하려면, 실패할 때는 반드시 시끄러워야 한다
원칙

가장 위험한 건 조용한 실패다. "정상이면 조용히"는 "실패하면 반드시 알린다"와 짝이어야 한다.

02 고민고민 4 · 한 곳이 멈추면

노트북 한 대가 꺼지면 서비스도 꺼져야 하는가

무슨 일이 있었나
  • 맥이 잠들면 수집이 멈췄다
  • 운영 Redis DB 하나가 비활성으로 삭제되자 구독자 정보가 사라졌다
  • 백업은 노트북 한 대에만 있었다
  • Claude 사전 점검 실패와 Gemini 크레딧 소진이 겹쳐 두 호가 빠졌다 (10/24~25)
무엇을 고민했나

"only PM2 pushes to git"처럼 한 곳으로 몰아넣은 건 처음엔 해결책이었다. 그런데 그 한 곳이 꺼지면? 결국 멈추면 다 멈추는 지점을 내 손으로 만든 셈 아닐까?

무엇으로 정했나
  • 1년치 호를 미리 만들어 Redis 원장에
  • 클라우드가 매일 20:25에 먼저 승인, 맥은 거든다
  • 일일 백업으로 데이터를 노트북 밖에
결과

11월 5~7일 맥을 꺼 둔 동안에도 매일 07:00에 메일이 나갔다.

02 고민고민 5 · 비용과 한도

무료 한도는 기능의 문제인가, 설계의 조건인가

무슨 일이 있었나
  • Supabase 무료 프로젝트의 일시 중지, 임베딩 무료 한도
  • Gemini 선불 크레딧 소진
  • macOS 러너가 10배로 계산되는 Safari 점검 때문에 GitHub Actions 사용 시간이 바닥났다 (10/25)
무엇을 고민했나

한도는 언젠가 터지는 사고일까, 처음부터 설계에 넣어야 하는 조건일까? 매번 터지고 나서 옮길 게 아니라, 처음부터 무료이면서 꺼지지 않는 쪽을 골라야 하지 않을까?

무엇으로 정했나
  • 검사를 push 직전 로컬 훅으로 옮겼다
  • 포트폴리오는 CI를 없앴다
  • 상반기의 Vercel에서 하반기에는 Cloudflare로 모였다
대가

CI를 줄인 만큼 Firefox 검사가 빠졌고, 품질은 이제 push 직전 로컬 검사에 달려 있다.

02 고민고민 6 · 에이전트의 기억

매번 새로 시작하는 에이전트에게 어제의 사고를 어떻게 전하는가

무슨 일이 있었나
  • 고친 문제를 다음 세션의 에이전트가 다시 되돌렸다
  • "Duo"를 Surface Duo로 잘못 알아들었다
  • 운영 데이터를 건드리는 작업이 늘었다
무엇을 고민했나

에이전트는 매번 새로 시작하지 않나? 그렇다면 어제 무슨 일이 있었는지는 어디에 남겨야 할까? 문서와 커밋 메시지 말고 다른 데가 있을까? 규칙만 적으면, 다음 에이전트가 왜 그래야 하는지까지 알 수 있을까?

무엇으로 정했나
  • CLAUDE.md에 "이건 되돌리지 말 것, 그날 이런 일이 있었다"를 쌓았다
  • 모르는 제품명은 먼저 찾아본다
  • "말하기 전까지 읽기만"을 매번 첫 문장으로
원칙

운영 데이터는 기본이 읽기 전용이다. 드라이런, 본인에게만 보내는 테스트 발송, 백업 → dry-run → 적용 → 재현 확인.

02 고민고민 7 · 취향과 측정

마음에 드는가가 아니라, 무엇을 원하는지 먼저 정했는가

무슨 일이 있었나
  • 포트폴리오는 하루에 터미널 UI, 에디토리얼, Windows 95 화면을 차례로 올렸다가 되돌렸다 (4/21)
  • 상반기에 큰 리디자인을 9번 했다
  • 평가 도구는 12분 동안 대화 화면을 6번 바꿨다
무엇을 고민했나

만드는 데 드는 비용이 거의 0이 되니까 일단 만들어 보고 정하게 되지 않나? 그런데 그렇게 정하지 않은 비용이 쌓이고 있었던 건 아닐까? 마음에 드는지가 아니라 숫자로 정해야 하지 않을까?

무엇으로 정했나
  • 6개월 버틴 Windows 95 화면을 실제 사용 수치(8일간 33건 대 홈 588건)로 지웠다
  • "첫 화면이 늦다"는 느낌을 LCP 측정으로 바꾸고 고쳤다
  • 헤드리스가 아니라 실제 Chrome에서 쟀다
원칙

무엇을 원하는지 먼저 정하는 게 가장 큰 절약이다. 연구윤리도 같은 방식으로, 부탁하는 대신 지킬 수밖에 없는 구조(모델 이름 숨기기, IRB 전에는 꺼 둔 기록 스위치)로 만들었다.

고민 6과 연결

매번 새로 시작하는 에이전트에게는 "무엇을 했나"보다 "왜 했고 어디까지 확인했나"가 필요했다. 확인하지 못한 것을 적는 습관이 다음 검토의 출발점이 됐다.

결론3주차 정리 · 남은 고민

에이전트가 쓰는 속도가 빨라질수록, 사람의 일은 확인과 거부권으로 옮겨 간다

1

실제 기기는 사람 몫

실제 iPhone과 트랙패드의 감각은 에이전트가 확인하지 못한다.

2

줄인 검사의 대가

비용 때문에 CI를 줄인 만큼, 품질은 push 직전 로컬 검사에 달려 있다.

3

마지막 버튼의 무게

에이전트가 하루 100개 넘게 커밋하는 날, 마지막으로 병합 버튼을 누르는 사람이 무엇을 확인했는지가 품질을 정한다.

3주 정리

1주차는 모델이 능력을 쌓은 과정, 2주차는 판단을 맡는 모델과 하네스, 3주차는 그 하네스를 한 사람이 10개월 동안 고민하며 직접 만들어 간 기록이었다.
